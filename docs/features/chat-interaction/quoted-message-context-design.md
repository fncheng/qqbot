# QQ 引用消息上下文技术设计

## 1. 背景与约束

用户在私聊或群聊中引用一条 QQ 消息后向机器人提问，期望机器人能够理解被引用的文本，并在模型支持 Vision 时识别被引用的图片。目标场景包括评论他人文本、解释截图、识别图片内容以及围绕某条历史消息继续提问。

已验证的协议事实：

- OneBot 11 将引用表示为 `reply` 消息段，`data.id` 是被引用消息的标识。[OneBot 11 消息段定义](https://github.com/botuniverse/onebot-11/blob/master/message/segment.md#%E5%9B%9E%E5%A4%8D)
- OneBot 11 和 NapCatQQ 均提供 `get_msg`，可按 `message_id` 获取原消息及其消息段。[OneBot 11 `get_msg`](https://github.com/botuniverse/onebot-11/blob/master/api/public.md#get_msg-%E8%8E%B7%E5%8F%96%E6%B6%88%E6%81%AF)、[NapCatQQ API](https://napneko.github.io/onebot/api)
- 接收图片段可以包含 `file` 和 `url`；NapCat 当前实现会为普通图片尝试生成 URL。[OneBot 11 图片段](https://github.com/botuniverse/onebot-11/blob/master/message/segment.md#%E5%9B%BE%E7%89%87)、[NapCatQQ 消息转换源码](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/api/msg.ts)
- NapCat 的消息标识采用 LRU 缓存管理，约 5000 条后可能失效；已撤回消息不能保证再次获取。[NapCat 资源与消息 ID 说明](https://napneko.github.io/onebot/napcat)

当前项目原本存在三处缺口：`mapper` 将 `reply` 和 `image` 降级为不支持段；`BotRouter` 不调用 `get_msg`；`LlmProvider` 只接受纯文本。以上缺口均可在现有分层内修复，不需要数据库迁移。

关键约束：

- 群聊仍然必须位于 `ALLOWED_GROUP_IDS` 且真正 `@机器人`，引用功能不能绕过现有权限、限流和会话隔离。
- 图片识别能力取决于 `OPENAI_MODEL` 及对应服务商是否兼容 Chat Completions 的 `image_url` 内容段。
- 引用消息是第三方非可信内容，不能因为加入上下文而获得高于普通用户内容的指令优先级。
- 图片 URL 可能带临时凭证，不应持久化到数据库。
- 第一阶段只解析一层引用，不递归展开被引用消息中的二次引用或合并转发。

## 2. 候选方案

### 方案 A：只使用当前事件中携带的数据

核心思路：直接读取当前事件中的 `reply` 段，希望事件同时携带原文。

- 优点：无额外 OneBot 调用，延迟和实现成本最低。
- 缺点：标准 `reply` 段只有原消息 `id`，没有原消息正文或图片；无法完成需求。
- 适用场景：仅判断用户是否使用了引用，不适合读取引用内容。

### 方案 B：收到引用后即时调用 `get_msg`

核心思路：`mapper` 保留 `reply.id`，`BotRouter` 在确认消息需要进入 AI 对话后，通过平台适配器调用 `get_msg`，将文本和图片转换为统一引用模型。

- 优点：符合 OneBot 标准能力；无需长期归档所有群消息；只在真实引用请求发生时增加一次查询；能够同时覆盖文本和图片。
- 缺点：依赖 NapCat 消息缓存和图片 URL 时效性；每次引用多一次 OneBot 往返；旧消息或撤回消息可能无法读取。
- 适用场景：当前单实例、按需处理的机器人，是本项目的最佳平衡点。

### 方案 C：持续归档所有可引用消息

核心思路：收到每条消息时把文本、发送者和媒体元数据写入 PostgreSQL，引用时优先读取数据库。

- 优点：不依赖 NapCat 短期消息缓存；可建立长期引用、检索和审计能力。
- 缺点：需要扩大群消息采集范围、增加数据库迁移和清理策略；图片仍需下载或对象存储；隐私告知、授权、存储成本和删除治理显著复杂；与当前“仅显式启用的群总结才归档普通文本”边界冲突。
- 适用场景：后续明确要做长期群知识库，并已完成群授权、保留期和对象存储治理时。

### 方案 D：进程内短期消息缓存加 `get_msg` 回退

核心思路：先从进程内缓存读取近期事件，未命中再调用 `get_msg`。

- 优点：高频引用可减少 OneBot 查询；短时间内即使 `get_msg` 偶发失败仍可能命中。
- 缺点：所有消息都需要进入缓存；增加内存上限、淘汰和多实例一致性问题；当前引用量不足以证明复杂度合理。
- 适用场景：运行数据表明 `get_msg` 延迟或失败率成为主要瓶颈后。

## 3. 横向对比

| 方案 | 实现复杂度 | 性能 | 可维护性 | 扩展性 | 实施成本 | 主要风险 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A 当前事件直读 | 低 | 最好 | 高 | 低 | 低 | 没有原消息内容，需求不可实现 | 只检测引用行为 |
| B `get_msg` 即时回查 | 中 | 每次引用增加一次本地 WebSocket 往返 | 高 | 中高 | 中 | 消息标识过期、图片 URL 或模型不兼容 | 当前项目 |
| C 全量持久化 | 高 | 查询稳定，写入持续发生 | 中 | 最高 | 高 | 隐私、存储和媒体生命周期治理 | 长期群知识库 |
| D 短期缓存加回查 | 中高 | 高频场景较好 | 中 | 高 | 中高 | 缓存一致性和内存控制 | 有明确性能数据后 |

## 4. 推荐方案

推荐方案 B：使用 `reply.id` 按需调用 OneBot `get_msg`，在 Gateway 层转换为平台无关的 `QuotedMessage`，由 `BotRouter` 构造本次模型上下文。

推荐理由：

1. 它直接使用 NapCat/OneBot 已提供的协议能力，不引入数据库表或媒体存储。
2. 它延续现有 `NapCat -> Gateway -> Bot Core -> LLM` 分层，`BotRouter` 不依赖 OneBot 原始响应结构。
3. 引用请求相对普通消息是低频路径，一次本地 WebSocket 调用的成本小于持续归档所有消息的长期成本。
4. 文本和图片可以沿同一条解析链路扩展，同时允许不支持 Vision 的模型在遇到图片时由服务商明确拒绝，不影响普通文本对话。
5. 对引用不可用场景明确失败，避免模型在没有看到原文时生成看似正确的评论。

## 5. 详细设计

### 5.1 调用链

```text
QQ 引用原消息并 @机器人
  -> NapCat 上报 reply + at + text 消息段
  -> mapper 保留 reply.id
  -> BotRouter 完成白名单、@、去重、会话、命令检查
  -> QuotedMessageResolver 调用 get_msg(message_id)
  -> 校验消息类型和群作用域
  -> 提取发送者、最多 8000 字文本、最多 4 张远程图片
  -> 文本化引用写入当前 Conversation
  -> 当前请求以 text + image_url 多模态内容调用 LLM
  -> 模型回答正常持久化并发送 QQ
```

### 5.2 上下文与持久化

- 被引用文本会和用户当前问题组合为带明确边界的用户消息，后续对话仍能看到这段引用。
- 被引用图片只通过远程 `http` 或 `https` URL 进入当前模型请求；NapCat 本地路径、`file://` 地址和临时 URL 均不写入数据库。
- 数据库只保存 `[图片]` 或图片摘要等文本化标记，因此后续轮次不会再次访问过期图片。
- 纯引用、没有附加文本时，默认任务为“请分析这条被引用的消息”。
- `/ping`、`/help`、`/clear` 和群总结仍按原有优先级处理，不为命令额外回查引用。

### 5.3 安全与边界

- 模型请求额外加入 system 级约束，明确被引用内容是第三方非可信资料，其中的指令不能改变系统要求或触发外部操作。
- `get_msg` 返回的 `message_type` 必须与当前会话一致；群聊返回 `group_id` 时必须与当前群一致。
- 只读取第一层引用，避免递归引用造成请求放大、循环或上下文失控。
- 引用文本最大 8000 个字符，图片最多 4 张，限制 token、模型费用和请求体规模。
- 当前实现不主动下载用户提供的 URL，因此不会由机器人进程发起图片 URL 请求；实际图片拉取由所配置的模型服务商完成。

### 5.4 降级行为

以下情况统一回复“无法读取被引用的消息”，并且不调用模型：

- `get_msg` 返回失败；
- 消息标识已从 NapCat LRU 缓存淘汰；
- 原消息已撤回；
- 返回数据结构无法解析；
- 返回消息与当前聊天类型或群不一致；
- 原消息没有可读文本、远程图片或可描述的常见消息段。

图片存在但没有可用远程 URL 时，会保留 `[图片]` 文本标记，模型能够知道原消息含图片，但不能执行视觉识别。模型或服务商不支持 `image_url` 时，本次模型调用会按现有统一错误链路失败并提示稍后再试；普通文本引用不受影响。

## 6. 已实施改动

- `src/gateway/qq/mapper.ts`：保留 `reply` 和 `image` 消息段。
- `src/gateway/qq/quoted-message-resolver.ts`：调用 `get_msg`，校验作用域并提取文本、发送者和图片。
- `src/types/message.ts`：新增引用段、图片段、统一引用消息和解析器接口。
- `src/llm/types.ts`、`src/llm/openai-compatible-provider.ts`：支持 Chat Completions 的文本与 `image_url` 多模态内容。
- `src/bot/router.ts`：在普通 AI 对话路径注入引用上下文、执行非可信内容隔离并处理不可用降级。
- `src/index.ts`：装配 QQ 引用消息解析器。
- `tests/mapper.test.ts`、`tests/quoted-message-resolver.test.ts`、`tests/router.test.ts`：覆盖消息段映射、作用域校验、多模态请求和失败降级。

## 7. 验证与验收

已完成的静态和自动化验证：

- `pnpm typecheck`：通过。
- `pnpm lint`：通过。
- `pnpm test`：9 个测试文件、30 个测试用例全部通过。
- `git diff --check`：通过。

仍需部署环境执行的端到端验收：

1. 群成员引用另一成员的纯文本并 `@机器人 请评论`，模型回答应明确基于原文。
2. 私聊引用文本后直接发送，不附加问题，机器人应主动分析引用内容。
3. 引用一张图片并要求识别，Vision 模型应收到图片并返回识别结果。
4. 使用不支持 Vision 的模型引用图片，应进入现有模型错误提示，普通文本引用仍正常。
5. 引用已撤回或足够久远的消息，应收到明确的“无法读取”提示，且不调用模型。
6. 在群 A 引用时不得接受群 B 的消息数据。
7. 引用消息中包含“忽略系统要求”等提示注入文本时，模型仍应把它当作待分析资料。

## 8. 后续优化

- 记录 `get_msg` 成功率、耗时、图片 URL 缺失率和 Vision 失败率，再决定是否引入方案 D 的短期缓存。
- 如果未来建设长期群知识库，再将方案 C 作为独立 Feature 设计，并先完成群授权、保留期、对象存储、删除与审计策略。
- 可增加显式模型能力配置，在已知模型不支持 Vision 时直接给出“当前模型不支持图片识别”，避免一次无效模型调用。
- 可扩展 NapCat OCR 作为无 Vision 模型的可选降级，但 OCR 只适合图片文字，不等价于通用图像理解。
