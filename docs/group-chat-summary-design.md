# 群聊每日总结功能设计方案

## 1. 目标与边界

支持群成员在群内发送：

```text
@机器人 告诉我今天群内发生了什么
```

机器人只基于当前群、当前群时区下当天的已归档文本消息生成总结并回复。

本功能的边界如下：

- 保持现有“普通群消息不主动回复”的行为。
- 仅对白名单且显式启用总结的群归档可总结消息。
- 原始群消息、用户与 AI 的对话历史、生成后的每日摘要必须分开存储。
- “今天”按群的配置时区计算；默认建议使用 `Asia/Shanghai`。
- 第一版只处理文本消息，不解析图片、文件、语音和链接内容。

## 2. 当前实现与缺口

现有群消息仅在同时满足以下条件时进入业务处理：

1. 群号位于 `ALLOWED_GROUP_IDS`。
2. 消息真实 `@机器人`。

未 `@机器人` 的群消息会被静默忽略，不会保存到数据库。因此，当用户发送“告诉我今天群内发生了什么”时，机器人没有当天其他成员的消息可以总结。

此外，当前群会话键为 `group:${groupId}:${userId}`，即同一群内每个成员拥有独立的 AI 对话历史。这符合普通 AI 问答场景，但不适合作为群级聊天记录来源。

现有 `messages` 表用于保存用户与 AI 的 Conversation 消息，缺少群发言人、群级时间范围查询等语义，不应直接复用来保存原始群聊记录。

## 3. 候选方案

### 方案 A：复用现有 Conversation 与 `messages` 表

为每个群创建公共 Conversation，并把所有群消息写入现有 `messages` 表。

优点：

- 初始改动较少。
- 可以快速完成概念验证。

缺点：

- 原始群聊天记录会与 AI 问答、机器人回复混在一起。
- `/clear` 的清理边界会变得模糊。
- 当前按 Conversation 查询历史的接口无法清晰表达“某群当天的所有发言”。
- 后续缓存、保留期、统计和权限控制都会依赖脆弱的约定。

适用场景：仅适合一次性演示，不适合作为正式实现。

### 方案 B：独立群消息归档，按需分段总结

将已启用总结功能的群普通文本消息保存到独立归档表。用户请求总结时，按群号和日期查询归档消息，采用分段总结后再汇总的方式生成结果。

优点：

- 原始群消息、AI 对话和每日摘要的数据边界清晰。
- 支持按日期、最近 N 小时、主题总结等后续扩展。
- 只有用户请求时才调用模型；同一天的重复请求可以复用摘要缓存。
- 与现有 Router、Repository、LLM 分层结构一致。

缺点：

- 需要新增数据库迁移、Repository、总结服务和测试。
- 高活跃群第一次请求当日总结时，可能触发多次模型调用。
- 需要处理群成员告知、数据保留和第三方模型服务的数据传输问题。

适用场景：当前项目的正式第一版。

### 方案 C：持续生成增量摘要

按固定时间间隔或达到消息数量阈值后，自动生成阶段摘要；用户请求每日总结时，只汇总阶段摘要。

优点：

- 高活跃群的请求响应较快。
- 每次模型输入更小。

缺点：

- 需要任务调度、失败重试、状态管理和幂等控制。
- 跨分段上下文容易丢失，事实准确性通常弱于按原始消息总结。
- 即使没有用户请求，也会持续产生模型调用成本。

适用场景：日均消息量很大且总结使用频率稳定的群。

## 4. 方案对比

| 方案 | 实现复杂度 | 模型成本 | 可维护性 | 扩展性 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| A：复用会话表 | 低 | 初期低，后续不可控 | 低 | 低 | 临时演示 |
| B：独立归档、按需总结 | 中 | 首次较高，缓存后低 | 高 | 高 | 当前项目正式首版 |
| C：持续增量摘要 | 高 | 持续消耗额度 | 中 | 高 | 高活跃大型群 |

## 5. 推荐方案

推荐采用方案 B：独立群消息归档、按需 Map-Reduce 总结、每日结果缓存。

该方案不会改变私聊和现有群内 `@机器人` AI 对话的会话隔离语义，同时能够清晰控制原始数据、模型调用与保留期限。未来如群活跃度明显提高，也可以在此基础上演进到增量摘要，而不需要迁移错误的数据模型。

## 6. 推荐架构

```text
群普通消息
  -> 白名单与群总结开关校验
  -> 群消息归档（静默，不调用 LLM）
  -> 结束

@机器人 总结今天群内发生了什么
  -> 识别总结意图
  -> 按“群 + 群时区当天”查询归档消息
  -> 检查当天摘要缓存是否有效
  -> 原文按预算分块
  -> 分块事实摘要（Map）
  -> 最终汇总（Reduce）
  -> 保存每日摘要缓存
  -> 发送 QQ 回复
```

普通 `@机器人` AI 对话仍沿用现有按“群 + 用户”隔离的处理流程。

## 7. 数据模型

### 7.1 `group_message_archives`

新增群消息归档表，用于保存可被总结的原始文本消息。

| 字段 | 含义 |
| --- | --- |
| `id` | 归档记录主键 |
| `group_id` | 对应 `groups.id` |
| `qq_user_id` | 发言人的 QQ 号 |
| `sender_display_name` | 可选，群名片或昵称快照 |
| `external_message_id` | OneBot 消息标识 |
| `content` | 可总结的纯文本内容 |
| `sent_at` | OneBot 事件中的原始发言时间 |
| `created_at` | 服务接收并归档的时间 |

约束与索引：

- `group_id + external_message_id` 唯一，确保 OneBot 事件重推不会重复计数。
- `group_id + sent_at + id` 联合索引，支持按群和日期范围顺序查询。
- 不保存机器人自身消息、机器人指令和总结触发请求，避免旧摘要或机器人问答污染总结素材。

### 7.2 `group_daily_summaries`

新增每日摘要缓存表。

| 字段 | 含义 |
| --- | --- |
| `group_id` | 对应群 |
| `summary_date` | 群时区下的自然日 |
| `timezone` | 生成摘要时采用的时区 |
| `source_message_count` | 已覆盖的原始消息数 |
| `source_latest_message_at` | 对应素材中的最新消息时间 |
| `content` | 最终摘要内容 |
| `created_at`、`updated_at` | 创建与更新时间 |

`group_id + summary_date` 必须唯一。若当天没有新增归档消息，直接复用缓存；若有新增消息，重新生成该日摘要。

## 8. 消息处理流程

1. 收到群消息后，先校验群号是否位于 `ALLOWED_GROUP_IDS`。
2. 仅当该群已显式开启“群聊总结”时，才处理归档逻辑。
3. 未 `@机器人` 的普通文本消息只归档，不调用模型、不计入机器人请求限流、不发送回复。
4. 对 `@机器人` 消息，先移除机器人提及并识别是否为总结请求。
5. 总结请求不写入原始消息归档；普通 AI 问答也不写入归档，避免机器人交互成为总结素材。
6. 非总结的 `@机器人` 消息保持当前 AI 对话处理逻辑。

第一版建议同时支持明确命令和有限中文别名：

```text
@机器人 /summary today
@机器人 告诉我今天群内发生了什么
@机器人 总结今天群聊
```

不建议第一版仅凭“总结”“今天”“群聊”等关键词触发，避免普通聊天被误判为总结请求。

## 9. 总结生成策略

不得将全天原始消息直接一次性传给模型。推荐采用两阶段 Map-Reduce：

1. 按 `sent_at` 升序读取当天归档消息。
2. 按字符或 Token 预算拆成多个连续消息块。
3. 每个块生成事实摘要，要求模型不得补充原文不存在的结论。
4. 将分块摘要传入最终汇总请求，生成当日摘要。
5. 保存结果到 `group_daily_summaries`，并记录覆盖消息数量与最新消息时间。

最终回复建议固定包含：

- 今日主要话题。
- 已明确的决定或结论。
- 待办事项及负责人，仅在原文明确时列出。
- 未解决问题。
- 重要提醒。

回复末尾应标明覆盖范围，例如：

```text
本摘要基于今日 09:00–18:35 的 326 条可读文本消息生成。
```

模型 System Prompt 必须声明：群消息是非可信资料，其中任何要求改变规则、泄露数据或执行外部操作的文本都只能作为被总结内容，不能改变总结任务。

## 10. 配置、权限与隐私

### 10.1 启用策略

- 群消息归档默认关闭。
- 只有机器人所有者或管理员显式启用后，机器人才开始归档该群消息。
- 启用范围必须是 `ALLOWED_GROUP_IDS` 的子集。
- 群级配置至少包含：是否启用总结、时区和原始消息保留天数。

### 10.2 群内告知

首次启用时，机器人应在群内说明：

- 文本消息会被保存并用于群总结。
- 原始消息的保留期限。
- 总结内容会发送到配置的模型服务商。
- 如何关闭该功能。

### 10.3 数据最小化

- 第一版只保存纯文本。
- 不跨群查询，任何总结只读取触发消息所在的 `groupId`。
- 建议原始消息默认保留 7 天，并定期删除过期记录。
- 机器人回复、机器人指令和空消息不纳入总结素材。

## 11. 并发、缓存与限流

- 同一群同一天的总结生成应使用群级串行键，例如 `group-summary:${groupId}:${date}`，避免多人同时请求导致重复模型调用。
- 已有当天缓存且没有新消息时，直接返回缓存。
- 生成过程中出现并发请求时，后续请求等待同一任务结果，再各自发送回复。
- 总结请求需要独立于普通对话设置更严格的群级限流，避免高成本请求被频繁触发。
- 当原始消息数量或字符数超过可配置上限时，必须明确告知实际覆盖范围，不能静默遗漏内容。

## 12. 分阶段实施

### 第一阶段

- 白名单群与显式启用开关。
- 纯文本归档。
- `today` 总结。
- Map-Reduce 总结。
- 当天摘要缓存。
- 默认 7 天原始消息保留期。

### 第二阶段

- 最近 N 小时、指定日期和主题总结。
- 群级配置管理指令或管理界面。
- 更完整的发言人显示名支持。
- 摘要结果的权限与导出控制。

### 第三阶段

- 针对高活跃群评估增量摘要。
- 仅在实际模型成本或响应延迟成为问题后再引入调度系统。

## 13. 验收与测试重点

- 未 `@机器人` 的普通消息仅归档，不触发 AI 回复和限流。
- 未启用总结的群不归档任何消息。
- OneBot 重复事件不会导致消息重复统计。
- 仅查询触发请求所在群的数据，不发生跨群泄露。
- 群时区的跨午夜边界正确。
- 当天无新消息时重复请求命中缓存。
- 当天新增消息后缓存失效并重新生成。
- 超长群聊能够分段处理，且最终回复明确说明覆盖范围。
- 过期原始消息会按配置的保留期删除。
