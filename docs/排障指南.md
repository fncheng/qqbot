# QQ Bot 排障指南

本文用于排查本项目在 Linux 服务器上通过 `docker-compose.server.yml` 部署时的常见问题。命令默认在部署目录 `/opt/qqbot` 执行。

## 0. 先确认服务现状

```bash
cd /opt/qqbot
sudo docker compose -f docker-compose.server.yml ps
sudo docker compose -f docker-compose.server.yml logs --tail=200 qq-bot napcat postgres
curl -i http://127.0.0.1:3000/health/live
curl -i http://127.0.0.1:3000/health/ready
```

判断标准：

- `/health/live` 返回 HTTP `200`：QQ Bot 进程已经启动。
- `/health/ready` 返回 HTTP `200`：PostgreSQL 和 NapCat OneBot WebSocket 都已连接。
- `/health/ready` 返回 HTTP `503`：进程仍在运行，但 PostgreSQL 或 NapCat 至少有一项未就绪。

## 1. 提示 `docker: command not found`

### 原因

服务器尚未安装 Docker Engine 或 Docker Compose Plugin，不能执行 Compose 部署、日志查看或容器状态检查。

### 处理方式

按照 [部署指南](deployment.md) 的“安装 Docker Engine 和 Docker Compose”章节安装。安装后确认：

```bash
docker version
docker compose version
```

未安装 Docker 时，不应根据配置文件推断容器已经成功启动。

## 2. `qq-bot` 反复重连或 `/health/ready` 返回 503

### 原因

通常是 NapCatQQ 未登录、OneBot WebSocket 服务端未启用、Token 不一致，或者 WebSocket 地址配置错误。

### 处理方式

先查看三个服务的日志：

```bash
sudo docker compose -f docker-compose.server.yml logs --tail=200 qq-bot napcat postgres
```

服务器专用 Compose 已将机器人连接地址固定为 `ws://napcat:3001`。在 NapCat WebUI 中应创建并启用以下配置：

| 项目 | 正确值 |
| --- | --- |
| 连接类型 | WebSocket 服务端（OneBot 11 正向 WebSocket） |
| 监听地址 | `0.0.0.0` |
| 端口 | `3001` |
| 消息上报格式 | `array` |
| 上报自身消息 | 关闭 |
| Token | 与 `.env` 中 `NAPCAT_TOKEN` 完全一致 |

本项目是 WebSocket 客户端，不能把 NapCat 配置成 WebSocket 客户端；也不能让 NapCat 在容器内只监听 `127.0.0.1`，否则 `qq-bot` 容器无法连接。

## 3. 基础 Compose 无法连接宿主机上的 NapCat

### 现象

使用 `docker-compose.yml` 启动机器人和 PostgreSQL，而 NapCat 运行在 Docker 宿主机时，日志显示 WebSocket 连接失败。

### 原因

容器内的 `127.0.0.1` 指向机器人容器自身，并不是 Docker 宿主机。

### 处理方式

在 `.env` 中填写：

```dotenv
NAPCAT_WS_URL=ws://host.docker.internal:3001
```

基础 Compose 已配置 Linux 所需的 `host-gateway` 映射。宿主机上的 NapCat 还必须允许 Docker 网络访问其 `3001` 端口；如果它只监听 `127.0.0.1`，容器仍然无法连接。

> `docker-compose.server.yml` 已在同一 Compose 网络中通过服务名连接 NapCat，不需要也不应手动设置为 `host.docker.internal`。

## 4. 私聊正常，群聊不回复

依次检查：

1. 机器人 QQ 账号已经加入目标群。
2. `.env` 的 `ALLOWED_GROUP_IDS` 包含正确的群号；多个群号使用英文逗号分隔。
3. 群消息使用 QQ 的真实 `@机器人` 功能，而不是输入机器人昵称。
4. NapCat 的消息上报格式是 `array`，而不是字符串消息。
5. 修改 `.env` 后已重新创建机器人容器：

```bash
sudo docker compose -f docker-compose.server.yml up -d --force-recreate qq-bot
```

群白名单为空时，机器人会忽略所有群消息，这是预期行为。

## 5. Docker 中修改 `.env` 后配置没有生效

### 原因

环境变量只会在容器创建时读取，单纯编辑 `.env` 不会更新正在运行的容器。

### 处理方式

```bash
cd /opt/qqbot
sudo docker compose -f docker-compose.server.yml up -d --force-recreate qq-bot
sudo docker compose -f docker-compose.server.yml logs --tail=100 qq-bot
```

常见需要重新创建容器的配置包括：`ALLOWED_GROUP_IDS`、`NAPCAT_TOKEN`、`OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`、`LLM_REASONING_EFFORT` 和系统提示词。

## 6. 使用 DeepSeek、通义千问或智谱后模型请求失败

### 原因

项目已使用 OpenAI-compatible `Chat Completions` 接口。模型服务商必须支持该协议，且 API Key、基础地址和模型名称必须属于同一服务商与账号。

如果设置了 `LLM_REASONING_EFFORT`，服务商还必须支持标准 `reasoning_effort` 参数。留空不会发送该字段；`none` 请求关闭推理，其他可选值为 `minimal`、`low`、`medium`、`high`、`xhigh`。不支持该字段或该强度的模型通常会返回参数错误，此时应清空该配置或改用服务商支持的模型和强度。

`OPENAI_API_KEY` 是历史变量名；接入第三方服务时填写该服务商自己的 API Key，并非 OpenAI API Key。

### DeepSeek

```dotenv
OPENAI_API_KEY=你的DeepSeekAPIKey
OPENAI_BASE_URL=https://api.deepseek.com
OPENAI_MODEL=deepseek-flash
```

### 阿里云百炼通义千问

```dotenv
OPENAI_API_KEY=你的百炼APIKey
OPENAI_BASE_URL=https://你的WorkspaceId.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
OPENAI_MODEL=qwen3.8-flash
```

百炼的 API Key、业务空间 ID 与地域地址必须匹配。应根据实际开通地域替换示例中的北京域名。

### 智谱 GLM

```dotenv
OPENAI_API_KEY=你的智谱APIKey
OPENAI_BASE_URL=https://open.bigmodel.cn/api/paas/v4
OPENAI_MODEL=你在智谱控制台可用的模型ID
```

当前项目会向基础地址追加 `/chat/completions`，最终调用 `https://open.bigmodel.cn/api/paas/v4/chat/completions`。不要填写 `https://open.bigmodel.cn/api/anthropic`，该地址使用 Anthropic 协议，与本项目的 OpenAI SDK 调用方式不兼容。

服务商返回“模型不存在”“无权限”或未返回文本时，优先核对 `OPENAI_MODEL` 是否是当前账号可用的模型 ID，再核对 API Key 和基础地址。

## 7. 仍在使用旧镜像，第三方模型配置无效

### 原因

第三方模型支持依赖项目的 OpenAI-compatible `Chat Completions` 适配器。服务器如果仍在运行更新前的镜像，旧镜像会调用 `Responses API`，部分服务商不支持该接口。

### 处理方式

将 `.env` 中的 `QQ_BOT_IMAGE` 改为包含该适配器的新发布版本，然后拉取并启动：

```bash
cd /opt/qqbot
sudo docker compose -f docker-compose.server.yml pull qq-bot migration-files
sudo docker compose -f docker-compose.server.yml up -d qq-bot
sudo docker compose -f docker-compose.server.yml logs --tail=100 qq-bot
```

如果在本地源码目录使用基础 Compose，必须重新构建并启动机器人容器：

```bash
docker compose up -d --build qq-bot
```

## 8. NapCat WebUI 无法从浏览器打开

### 原因

服务器 Compose 将 WebUI 的 `6099` 端口绑定到服务器 `127.0.0.1`，不允许直接从公网访问，这是安全设计。

### 处理方式

在自己的电脑建立 SSH 隧道：

```bash
ssh -L 6099:127.0.0.1:6099 <服务器用户名>@<服务器公网IP>
```

保持该命令运行，然后访问 `http://127.0.0.1:6099/webui`。首次登录 Token 从 `napcat` 日志获取：

```bash
sudo docker compose -f docker-compose.server.yml logs --tail=200 napcat
```

WebUI 登录 Token 与 OneBot 的 `NAPCAT_TOKEN` 是两种不同用途的凭据，不能混用。

## 9. PostgreSQL 初始化迁移未执行

### 原因

`migration-files` 会将初始 SQL 复制到命名卷，PostgreSQL 仅在首次创建 `postgres_data` 数据卷时执行初始化 SQL。已有数据卷不会自动再次执行初始化脚本。

### 处理方式

检查初始化容器：

```bash
sudo docker compose -f docker-compose.server.yml ps -a migration-files
sudo docker compose -f docker-compose.server.yml logs migration-files
```

`migration-files` 的正常状态为退出码 `0`。对于已有数据库，应先检查实际表结构，再按迁移内容人工执行需要的 SQL；不要为了重跑初始化而删除数据卷。

## 10. 数据保护与高风险命令

以下命令会删除 PostgreSQL 数据、NapCat 登录状态及配置卷，除非明确准备清空全部数据，否则不得执行：

```bash
sudo docker compose -f docker-compose.server.yml down -v
```

日常停止服务应使用不带 `-v` 的命令：

```bash
sudo docker compose -f docker-compose.server.yml down
```

`.env` 包含 API Key、数据库密码和 OneBot Token。不要提交到 Git、发送到聊天记录或用发布包模板覆盖生产 `.env`。
